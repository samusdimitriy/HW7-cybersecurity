Лабораторна робота
Практичний аналіз залежностей npm-пакета з використанням SCA-інструментів

Зараз ви виконаєте лабораторну роботу, яка, якщо дивитися з точки зору реального SSDLC, збігається з практикою десь на 60–70%. Вона дуже близька за логікою, але є кілька відмінностей через те, що в продакшн-процесі багато речей робляться автоматично та на певному етапі життєвого циклу.



Давайте розглянемо, що збігається з реальністю:

Використання таких SCA-інструментів, як Syft, Grype та OSV-Scanner. Вони реально застосовуються в CI/CD.
Генерація SBOM і подальше сканування застосунку. Це безпосередній елемент SSDLC (на етапі build).
Оцінка вразливостей через CVSS / EPSS. У великих компаніях це робиться для пріоритезації їх закриття.
Ліцензійний аудит. Він справді є обов’язковим для enterprise.
Використання кількох джерел даних (CVE DB, OSV, Snyk тощо). Теж відповідає практиці.


Що відрізняється від реального процесу

1. Автоматизація процесу. У реальному SSDLC SCA-сканери інтегровані в CI/CD (GitHub Actions, GitLab CI, Jenkins), і після кожного коміту або білду:

автоматично збирається SBOM;
автоматично запускається сканування;
результат передається в систему трекінгу (Jira, Azure DevOps);
критичні проблеми можуть автоматично блокувати збірку.
У лабораторній ви все зробите вручну, щоб зрозуміти, як працюють інструменти.

2. Контекст уразливостей. У реальному проєкті аналіз того, чи вразлива залежність реально використовується в коді (Reachability analysis), часто робиться автоматично.

У лабораторній цей етап можна зробити лише теоретично (через пошук у коді).

3. Момент запуску SCA. У реальності SCA запускають автоматично:

при додаванні нової залежності (pre-commit hook або pull request check);
під час збірки коду (build);
з певною періодичністю в продакшені (continuous monitoring).
У лабораторній ви це зробите тільки один раз, вручну.

4. Масштаб і швидкість. У продакшені SCA автоматично проганяє десятки / сотні пакетів за секунди. У лабораторній ви будете працювати з трьома пакетами для прикладу.

5. Інтеграція з Issue Tracker та Policy Engine. У реальних SSDLC результати автоматично потрапляють у backlog з уже визначеним пріоритетом. Діють політики: наприклад, «не дозволяти збірку, якщо CVSS ≥ 7.0». У лабораторній цього немає.



💡У чому цінність такої лабораторної
Вона дозволить побачити «нутрощі» процесу, які в продакшені приховані за автоматизацією.
Дасть змогу відчути логіку роботи інструментів і баз даних, а не просто натискати «Run pipeline».
Це фундамент для розуміння CI/CD-інтеграцій.


Мета цієї роботи: Закріпити навички роботи з інструментами Software Composition Analysis для виявлення вразливостей, аналізу залежностей та оцінки ліцензійного стану npm-пакетів.



Інструменти, які вам знадобляться

Socket.dev — потрібен для аналізу npm-пакета на наявність install scripts, обфускованого коду, ризикованих API-викликів. https://socket.dev
deps.dev — допоможе візуалізувати граф залежностей і переглянути дані про вразливості. https://deps.dev
OpenSSF Scorecard Viewer — оцінить гігієну розробки та безпеки проєкту. https://securityscorecards.dev/viewer
OSV-Scanner — знайде вразливості в залежностях із бази OSV. https://osv.dev
Syft — потрібен для генерації SBOM у форматі CycloneDX. https://github.com/anchore/syft
Grype — дозволяє просканувати SBOM на наявність вразливостей. https://github.com/anchore/grype
CVE Database — для ручного пошуку вразливостей (cvedetails, cve.mitre).
EPSS — допомагає оцінити ймовірності експлуатації знайдених CVE. https://www.first.org/epss/


Вихідні дані

Виберіть три npm-пакети (наприклад, express, lodash, axios, jsonwebtoken, event-stream, minimist, ua-parser-js, node-forge, xmldom), бажано не останніх версій.



Завдання

1. Виконати попередній аналіз пакета.

2. Побудувати граф залежностей.

3. Виявити відомі вразливості.

4. Оцінити безпекову гігієну проєкту.

5. Згенерувати SBOM та просканувати його.

6. Сформувати звіт з рекомендаціями.



Хід роботи

Крок 1. Попередній аналіз через Socket.dev

Перейти на https://socket.dev
У полі пошуку ввести назву пакета (наприклад, lodash).
Зробити скриншот розділу Overview.
Зробити висновок: чи є ознаки проблем.


Крок 2. Аналіз залежностей через deps.dev

Відкрити https://deps.dev
Знайти той самий пакет.
Переглянути граф залежностей та зафіксувати кількість прямих і транзитивних залежностей.
Зробити скриншот графа.


Крок 3. Оцінка безпекової гігієни через OpenSSF Scorecard

Перейти на https://securityscorecards.dev/viewer
Ввести URL репозиторію пакета.
Записати загальний бал і ключові зауваження.
Зробити скриншот результатів.


Крок 4. Автоматичний пошук вразливостей через OSV-Scanner

1. Встановити OSV-Scanner.

Для Linux-подібних ОС: go install github.com/google/osv-scanner/cmd/osv-scanner@latest

Для Windows спочатку встановити Node.js та npm (це обов’язково)

Для цього перейти на офіційний сайт: https://nodejs.org/en/download/
Завантажити LTS-версію для Windows.
Встановити з налаштуваннями за замовчуванням (галочку Add to PATH залишити увімкненою).





2. Перевірити працездатність через команди: node -v та npm -v

3. Встановити OSV-Scanner

Перейти в офіційний GitHub: https://github.com/google/osv-scanner/releases
Завантажити останній реліз osv-scanner-windows-amd64.exe.





Перейменувати файл в osv-scanner.exe і покласти в папку, що є в PATH (наприклад, C:\Windows\System32 або додати свою папку в PATH).
Перевірити успішну інсталяцію командою: osv-scanner --version
4. Створити папку з тестовим проєктом та додати залежність командами:

mkdir sca-test

cd sca-test

npm init -y

npm install lodash@4.17.19 (як приклад, вказано пакет lodash@4.17.19)

5. Запустити сканер командою: osv-scanner –recursive .

6. Записати знайдені CVE, їхні CVSS та дати публікації.



Крок 5. Ручний пошук CVE і оцінка EPSS

1. Відкрити cvedetails.com або cve.mitre.org.

2. Ввести назву пакета.

3. Визначити EPSS для кожної CVE через https://www.first.org/epss/ .



Крок 6. Генерація SBOM через Syft

1. Встановити Syft

Для Linux командою: curl -sSfL <https://raw.githubusercontent.com/anchore/syft/main/install.sh> | sh -s -- -b /usr/local/bin після чого перевірити працездатність: syft version

Для Windows:

Завантажити останній реліз з GitHub: https://github.com/anchore/syft/releases
Вибрати syft_windows_amd64.zip, розпакувати.
Покласти syft.exe у папку, яка в PATH.
Перевірити командою: syft --version
2. Запустити: syft dir:. -o cyclonedx-json > sbom.json

3.. Переглянути вміст sbom.json.



Крок 7. Сканування SBOM через Grype

1. Встановити Grype.

Для Linux: curl -sSfL <https://raw.githubusercontent.com/anchore/grype/main/install.sh> | sh -s -- -b /usr/local/bin після чого перевіряємо, чи працює: grype version

Для Windows:

Завантажити з GitHub: https://github.com/anchore/grype/releases
Вибрати grype_windows_amd64.zip, розпакувати.
Додати grype.exe в PATH.
Перевірити командою: grype --version
2. Запустити: grype sbom:sbom.json

3. Записати результати сканування.



Шаблон звіту

1. Загальні відомості (пакет, версія, репозиторій, дата аналізу)

2. Попередній аналіз (Socket.dev) — підозрілі ознаки, скриншот

3. Граф залежностей (deps.dev) — кількість залежностей, скриншот

4. Оцінка безпекової гігієни (OpenSSF Scorecard) — загальний бал, ключові зауваження, скриншот

5. Автоматичний пошук вразливостей (OSV-Scanner) — таблиця CVE з CVSS і рекомендаціями

6. Ручний пошук CVE і EPSS — таблиця CVE, CVSS, EPSS, опис, вплив

7. SBOM — кількість компонентів, формат, файл SBOM у додатках

8. Результати сканування SBOM (Grype) — таблиця CVE з рекомендаціями

9. Висновки та рекомендації — критичні проблеми, оновлення, додаткові заходи
